## 1. 背景 — 実際に起きた事故

2026-09-14、年配のお客さまが**確定金額の提示後に自由入力へ切り替えられず**、「買取を申し込む」「査定を申し込む」のタイルを連打した。

原因は3つが噛み合ったもの。いずれも**現行の仕様どおりの動作**であり、バグではない。

1. **入力欄が見えない**【検証済】 — 本番メニュー（管理画面製）の「メニューのデフォルト表示」が「表示する」、メニューバーのテキストが「メニュー」だった。メニューが開いた状態で表示され、画面下がタイルで埋まる。2026-09-14 に「表示しない」へ変更済み（§2-3）
   （旧版はリポジトリの `richmenu_A.json` の `selected: true` を根拠にしていたが、この JSON は本番に登録されていない）
2. **タイルがテキスト送信アクション**【検証済（コード側から）】 — 本番コードに postback の送り手は存在せず、テキスト分岐で受けている。タップのたびにタイルの送信テキストが顧客の発言として吹き出しに残る
3. **その文言が手動対応モードを解除する**【検証済】 — `MANUAL_RESET_TEXTS`（全14語）に、09-12 変更後のタイル文言「買取を申し込む」「写真は以上です」と旧文言「買取査定を申し込みます」「査定を申し込む」等が含まれる。タップのたびに `clearManualMode_` が走り、ボットが申込案内を自動返信する

さらに `notifyManualIncoming_` は10分のバースト抑制（`CacheService` 600秒）があるため、**連打されてもオーナー通知は1回しか飛ばない**。【検証済】

**業務影響:** 確定金額の提示後に顧客の意思表示が必要な場面で、その導線が自由入力しかなかった。特定商取引法・訪問購入における「顧客からの請求」の証跡が取れず、成約自体も落としている。

## 3. 機能要件

### F-1. 入力欄への到達性【確定】

- リッチメニューの初期状態を `selected: false` とし、**入力欄とカメラアイコンが常に見えている**こと
- `chatBarText` は開閉できると分かる文言にする（14文字以内）
- 顧客が自由入力に切り替えるために、操作説明の文章を読む必要がないこと

### F-2. タイルのアクション種別【確定】

- リッチメニューのタイルは `type: 'postback'` + `displayText` とする
- `type: 'message'` は使用しない
- `displayText` は残す（タップが効いたことの視覚的フィードバックとして年配の方に必要）
- **理由:** `data` が飛ばないと状態ガードが一切かけられない。また `/line/<slug>/` のプリセット文言サフィックスと混ざり、集計キーが汚れる

### F-3. 状態ガード【確定】

postback データのスキーマ:

```
v=2&flow=<flow>&step=<n>&act=<act>&val=<value>
```

| キー | 値 | 必須 |
|---|---|---|
| `v` | `2` 固定 | 必須 |
| `flow` | `satei` / `battery` / `area` / `faq` / `menu` | 必須 |
| `step` | `0`〜`6` | 必須 |
| `act` | `next` / `back` / `reset` / `stop` / `submit` / `consult` | 必須 |
| `val` | 回答値 | 任意 |

- 全 postback に `v` `flow` `step` を含める。省略可の運用にしない
- 受信時、保存中のセッション step と一致しなければ**進めない**
- `v` が無い data は旧キーとして変換表（F-9）を通す
- 変換表にも無い未知キーは「メニューから選び直してください」に落とす
- **過去のトーク履歴に残ったボタンは消えない。数日前のボタンを押される前提で設計すること**

### F-4. 手動対応モードの保護【確定】

- **人が対応している最中に、タイル1回で自動応答へ戻る挙動を廃止する**
- 手動対応中の新着は、オーナーへ通知するのみ。モードは維持する
- `MANUAL_RESET_TEXTS` / `MANUAL_RESET_ACTIONS` から申込系を除外する
  - **2026-09-14 応急処置として両リストを空にして本番 @47 にデプロイ済み**（申込系以外のタイルでも解除しない）
- 手動モードの解除は、オーナー側の明示操作（問い合わせ一元管理シート users タブの `manual_mode` 列を空にする）またはTTL満了（48時間）によってのみ行う
- 注: 分類不能テキストでも手動対応に入る（§7 #4）。1通送っただけのお客さまにもボットが48時間無応答になる前提で運用する（オーナー承認済み）
- **例外: サイトCTA（`/line/<slug>/` の経路識別子付き初回メッセージ）は解除する**（2026-09-14 オーナー決定。§6 #9）
- **通知のバースト抑制（現行10分）を見直す。** 連打が通知1回に潰れると、事故に気づけない

### F-5. 確定金額提示と請求の取得【確定・特商法の証跡に直結】

- ボットが訪問予約まで自動で進めてはならない
- 順序: ヒアリング完了 → **操作者が定額（範囲ではなく確定額）を提示** → 顧客がボタンをタップ
- ボタンは**吹き出しの中**（テンプレート / Flex）に置く。リッチメニューの開閉状態に影響されないこと
- 選択肢: `[この金額で決定]` / `[もう少し考えます]`（2026-09-15 確定。詳細は §10）
- 決定後は、ご希望の日時とお伺い先の住所（番地まで）を送ってもらい、以後は人が対応する
- 文言を弱めない（「日程を調整する」等に置き換えない）

**ログ要件（4項目）:**
- userId
- 提示額
- タップ時刻
- 表示していた文言のスナップショット

### F-6. 写真工程の専用メニュー【確定】

- 写真ステップに入ったら、`camera` / `cameraRoll` アクションを持つ専用リッチメニューに切り替える
- 構成: `[カメラで撮る]` / `[アルバムから選ぶ]` / `[写真なしで進む]`
- **タイルを押した瞬間にカメラが起動する**こと。カメラアイコンを探させる工程を消す
- 「画面下の🎥マークを押して…」のような操作説明を文章で書かないこと

### F-7. リッチメニューの状態遷移【確定】

3状態とする。

| 状態 | 用途 |
|---|---|
| 通常時 | 常設の入口 |
| フロー進行中 | 新しいフローを開始できないメニュー。戻る / やり直す / 相談 |
| 写真工程 | F-6 |

- 切替は `richmenuswitch`（リッチメニューエイリアス）
- **`richmenuswitch` は LINE アプリのバージョン依存。webhook 側でも `linkRichMenuIdToUser` を叩くフォールバックを必ず実装する**（`linkRichMenu_` が既にあるので流用可）
- 画像は1枚絵。分割線も画像側に描く。タップ領域は座標指定

### F-8. バッテリー診断の動画案内【確定】

- 診断方法（ボタン長押し）が理解されていないため、動画で案内する
- **お客さまから受け取った動画は使用しない**（著作権・信頼の問題）。自社撮影に差し替える
- 撮影要件: 縦 / 20〜30秒 / **音声なし前提で字幕のみ** / 固定撮影 / ボタン位置を最初に映す / 長押し中の秒数カウントを表示 / 指を離したあとの保持時間を映す / LEDが白飛びしない露出
- 配信: リポジトリの `video/` に置き、meguri-cycle.com から HTTPS 配信。LINE の動画メッセージにも使用
- **本数と残容量の対応は動画内で断定しない。** 本数の報告までで止める

### F-9. 旧入口の変換表【要作成】

- **旧 postback キーは実質存在しない**（§2-0。本番に postback を送る部品が無い）。変換表の対象は**テキスト**になる
- 棚卸し対象:
  - 管理画面製リッチメニューの全タイルの送信テキスト（§2-3 を実物で埋めてから）
  - テキスト分岐で完全一致受理している文言（旧文言の互換受理を含む。例: 「買取を申し込む」「買取査定を申し込みます」「買取査定を申し込む」）
  - `MANUAL_RESET_TEXTS`（14語）/ `isExplicitReRequest_` の受理文言
  - クイックリプライの送信テキスト（「写真は以上です」「電動アシストの案内を見る」等）
  - 念のため `MANUAL_RESET_ACTIONS` / `handlePostback_` の action 名（apply_kaitori 等）も v2 スキーマへの対応を書く
- 推測で書かず、実コードを読んで作ること
- webhook 冒頭で変換を通す
- 補足: クイックリプライは次のメッセージで消えるため、**過去トークに残って後から押されるのは主にリッチメニュー（切替後は旧メニュー自体が表示されない）と、新設計で導入するテンプレート / Flex ボタン**。F-3 の「数日前のボタン」対策は新設計側のボタンが主対象

### F-10. 流入元集計の維持【確定】

- `/line/<slug>/` のプリセット文言サフィックスは **GAS の集計キー**。1文字も変えない
- 新フローでもこれを入口として認識し、集計キーを維持すること
- `detectRouteId_` / `ROUTE_IDS` の扱いを引き継ぐこと

転送シムの要件:
- 対象 userId のイベントのみ転送
- `try/catch` で囲み、転送に失敗しても必ず 200 を返す
- 転送処理のいかなる例外も既存処理に波及させない
- 既存の共通関数をリファクタしない。独立した関数として追加する
- userId は PropertiesService に置く（ハードコードしない）

新プロジェクト側:
- 別 GAS プロジェクト、別 WebApp URL
- Sheets は**別ファイル**。本番台帳と集計シートには書き込まない
- リッチメニューは `linkRichMenuIdToUser` で対象 userId にのみ紐付け。デフォルトは旧メニューのまま

### N-3. 切替とロールバック【確定】

**切替（2アクション）**
1. `setDefaultRichMenu` を新メニュー ID に変更
2. 転送シムの userId 判定を解除

**ロールバック（2アクション）**

## 10. 確定金額提示の文言【確定 2026-09-15】

前提: `handoff_line_system.md` §4-4 の「条件付き確定額」を土台にする。金額は**操作者が手で入力**し、ボットは定型に流し込んで送るだけ（F-5「ボットが訪問予約まで自動で進めてはならない」）。
禁止: レンジ表記／「高価買取」「転売」／電話CTA／玄関先での交渉を前提とする表現／S3 以降の金額の自動送信。
有効期限は **7日間**（2026-09-16 オーナー決定。サイト全ページも14日→7日に修正して統一）。

### 10-1. 送信の形

Flex メッセージ1通。上から「金額」「条件」「ボタン2つ」。ボタンは吹き出し内（F-5）。

```

━━━━━━━━━━━━━━━━━━

【買取金額】 12,000円（確定）
　パナソニック ビビ・DX（電動アシスト）1台

この金額は、お写真のとおりであれば
お伺い当日にそのままお支払いします。
出張費・査定料はかかりません。
有効期限は ○月○日（7日間）です。

※ 写真では分からない次の点が当日見つかった
　場合だけ、その場では決めず、再査定のうえ

[ もう少し考えます ]

```

- 「（確定）」を金額の直後に置く。レンジに見える表記（「〜」「前後」「目安」）は使わない
- 「お持ち帰り」は使わず**「再査定」**とする（2026-09-15 オーナー決定）
- 電動アシストの場合、条件の3行目「バッテリー残量ランプが2点灯以下」を入れる。非電動なら省く
- 処分・引き取り（値段がつかない車体）の場合は「買取金額」の代わりに「引き取り費用」とし、`fee_master` の出張費を表示する（[[meguri-cycle-travel-fee-policy]]: 買取なら出張費無料、出張費がかかるのは値段がつかない車体の引き取りのみ）

### 10-2. 電動アシストの条件分岐（提示前のヒアリングで点灯数が取れている場合）

点灯数が確認済みなら 10-1 の単一額でよい。**未確認のときだけ**次の形にする（単一額を出せないため、条件ごとの確定額として3段で示す。レンジではない）。

```
【買取金額】 バッテリー残量ランプの点灯数で決まります
　4点灯以上 … 30,000円（確定）
　3点灯 　　 … 24,000円（確定）
　2点灯以下 … 18,000円（確定）

お伺い当日にランプを一緒に確認し、
該当する金額をそのままお支払いします。
```

- 各段の金額はすべて操作者が入力。ボットが計算・補完しない
- ボタンは 10-1 と同じ2つ。「この金額で決定」のログには3段すべてをスナップショットとして残す

### 10-3. 複数台

```
【買取金額】 合計 27,000円（確定）
　1台目　パナソニック ビビ・DX 　… 12,000円
　2台目　ブリヂストン アルベルト … 15,000円
```

1台ずつ内訳＋合計（handoff §5-5）。条件文・ボタンは10-1と同じ。

### 10-4. ボタンの postback と応答

| ボタン | data | ボットの応答 | 状態 |
|---|---|---|---|
| この金額で決定 | `v=2&flow=satei&step=5&act=submit&val=accept&q=<quoteId>` | 下記 10-4-1 の文（**希望日時と住所の詳細を送ってもらう**）→ **オーナー通知（即時・バースト抑制なし）＋手動対応ON** | S3 → S4 手前（日程・住所の確認は人が行う） |
| もう少し考えます | `v=2&flow=satei&step=5&act=submit&val=hold&q=<quoteId>` | 「承知しました。この金額は **○月○日まで（7日間）** 有効です。それまでに、下のボタンからいつでもお申し込みいただけます。」＋同じ2ボタンを再掲 → オーナー通知 | S3 のまま |

#### 10-4-1. 「この金額で決定」のあとの文

```
ありがとうございます。12,000円で決定しました。

お伺いの準備のため、次の2つをこのまま
入力して送ってください。

① ご希望の日時
　（例：9月20日 土曜 午前中／第2希望も
　　あれば助かります）
② お伺い先のご住所
　（市町名・町名・番地まで。マンション等は
　　建物名とお部屋番号も）

担当者が確認して、日時をご連絡します。
```

- 番地は金額決定後にはじめて聞く（handoff §10-5「住所は町名までしか自動で聞かない。番地は金額合意後」と整合）
- この文の直後は手動対応ON。お客さまの返信（日時・住所）はボットが解釈せず、そのままオーナー通知に載せる
- 送られた住所・日時は `quotes` の該当行に人が転記する（ボットは保存しない。個人情報の自動保存を増やさない）

#### 10-4-2. 共通ルール

- `q=<quoteId>` は提示ごとに採番（同じお客さまに再提示したとき、古いボタンが押されても**どの提示への回答か**を特定するため。F-3「数日前のボタンを押される前提」）
- 有効期限は提示日＋7日を既定とし、Flex 本文にも日付で明記する。期限切れの提示のボタンが押されたら「金額を再確認してご連絡します」と返してオーナー通知、金額は自動で再掲しない
- 同じ提示に2回目以降の同じボタンは無視（ログのみ）。accept のあとの hold は受理して通知（意思の変更として人が対応）
- 「もう少し考えます」で停止フラグは立てない。その後「やめます」等が来たときだけ立てる（§9-2 と同じ考え方）

### 10-5. ログ（F-5 の4項目＋α）

`quotes` シート（本番の問い合わせ一元管理シート内。N-2 の並行稼働中は新プロジェクト側の別 Sheets に同名タブ）

```
quoteId / userId / displayName / 提示時刻 / 提示者 / 台数 / 金額（合計）/ 内訳JSON
/ 条件文（送信した本文全文のスナップショット）/ 有効期限
/ 回答（accept|hold|expired）/ 回答時刻 / 回答時の本文スナップショット（ボタン直前に表示していたFlexのalt+本文）
```

- 保存年数は未確定事項 #10（kaitori 台帳の7年に揃える案）
- 「表示していた文言のスナップショット」は**送信時の本文全文**を保存する。あとで文言を変えても、当時お客さまが見た文がそのまま残る

### 10-6. 操作者の入口【確定: コマンド方式】

操作者（オーナー）が**自分の LINE からボットへ**コマンドを送る。ボットは送信元が `OWNER_LINE_USER_ID` のときだけコマンドとして解釈する（お客さまの発言と混ざらない）。管理画面チャットからの金額手打ちはしない（証跡と定型の統一のため）。

前提: ボットはお客さまごとに短い**お客さま番号**（`users` タブに `cust_no` 列を追加。例 `C12`）を採番し、オーナー通知のすべてに載せる。オーナーはその番号で相手を指定する。

```
#見積 C12 12000                      … 1台・単一額
#見積 C12 12000 パナソニック ビビDX   … 金額のあとは車体名（任意・本文に載る）
#見積 C12 12000 電動                  … 「電動」を含むとバッテリー条件行を追加
#見積 C12 30000/24000/18000 電動      … 点灯数未確認の3段（4点灯以上/3点灯/2点灯以下）
#見積 C12 12000+15000                 … 複数台（内訳。合計はボットが計算して表示）
#引取 C12 2500                        … 値段がつかない車体の引き取り費用
#見積 C12 12000 期限 9/30             … 有効期限の上書き（既定は提示日＋7日）
```

手順:
1. オーナーがコマンドを送る
2. ボットが**プレビュー**（実際に送る Flex そのもの）をオーナーに返し、`[送信する]` `[やめる]` の postback ボタンを付ける
3. 「送信する」で `quotes` に1行追加してお客さまへ push。「やめる」または5分放置で破棄
4. 送信前チェックで止まる条件: 禁止語（「高価買取」「転売」「〜円前後」「目安」「〜」）／対象ユーザーの `state` が S4 以降（handoff §10-4）／対象が停止フラグ中／お客さま番号が存在しない。理由をオーナーに返して送らない

- 金額は半角数字。カンマ有無どちらも可。0 円は `#引取` でのみ許可
- 車体名は複数台のとき `+` 区切りで対応させる（`#見積 C12 12000+15000 ビビDX+アルベルト`）
- 同じお客さまへの再提示は新しい quoteId。前の提示は `expired` にする（前のボタンが押されても金額を再掲しない）

## 11. 停止分岐（膨らみ・液漏れ・破損）の文言案（未確定事項 #7 の叩き台・2026-09-15）

前提（サイト `/dendo/` と統一。変えない）: **「膨張・液漏れ・破損がある → 安全上お受けできません。処分窓口をご案内します」**。
法令上の線引き: 使えないバッテリーは廃棄物。当方は一般廃棄物の収集運搬許可を持たないため、**「引き取ります」「処分します」「お預かりします」と言わない**。案内できるのは「相談先」まで。
自治体ごとの可否（金沢市の資源回収で膨張品可、など）は**ボットでは断定しない**（`HANDOFF.md` の電話確認待ち。確定後もコラムに書き、ボットはコラムへ誘導する）。

次のどれかがありますか？
　・ケースがふくらんでいる
　・液がもれている、液のあとがある
　・ひび割れ・落として壊れた

[ どれもない ]
[ ある ]
[ わからない ]
```

| ボタン | data |
|---|---|
| どれもない | `v=2&flow=satei&step=3&act=next&val=bat_ok` |
| ある | `v=2&flow=satei&step=3&act=stop&val=bat_ng` |
| わからない | `v=2&flow=satei&step=3&act=next&val=bat_unknown` |

（バッテリーフローでは `flow=battery&step=1`）

### 11-2. 「ある」→ バッテリーは停止、車体だけ査定へ【確定 2026-09-15】

　https://meguri-cycle.com/column/battery-disposal/

```
