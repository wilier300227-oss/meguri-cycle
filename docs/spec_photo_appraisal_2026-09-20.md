## 1. 目的と背景

- 現状、サイトとLINEで「写真3枚でOK」「数枚でOK」と案内している。その結果、現地で「思ったより錆びている」「お客さんも気づいていない不具合がある」ことが多く、確定額からの減額が起きている。
- 減額が続くと信頼が落ちるだけでなく、「確定額に合意 → お客さんから訪問を依頼」という訪問購入の前提も崩れやすい。
- 方針：写真をしっかり撮ってもらう設計に変え、状態の把握と減額の判断を**写真の段階**で済ませる。当日は金額を変えない。
- 写真が増えて離脱が増えるようなら見直す（「2.8 計測」で判断する）。

## 2. 確定事項

### 2.1 写真と金額のルール

1. 写真がそろわなくても、受付は先に進める。写真を理由に止めない。強制する感じを出さない。
2. 撮影リストの該当箇所がすべてそろっていれば、写真をもとにした実際の金額を出す。
3. 足りない場合は、枚数と内容を見てオーナーがその都度判断して減額する。「1枚いくら」の固定額は決めない。**ボットは金額を計算しない**（枚数の記録と通知だけ）。
4. 提示する確定額は常に1つの金額。幅は出さない（特商法・訪問購入の運用に合わせる）。
5. 付いていない部品（前カゴ・荷台など）は数えない。
6. 写っていない鍵・充電器は「ない」前提で金額を出す（一般車の鍵はボタンで回答）。お客さん向けの説明では「写っていないものは『ない』として金額を出します。あとで見つかったら教えてください」と、救済とセットで伝える。
7. バッテリーの型番シールが撮れなかった場合も、3 と同じくオーナーの都度判断。文字がぼやけて読めない場合は、減額の判断をする前に「そのシールだけ、もう1枚お願いします」とオーナーから頼む（ボットは判定しない）。
8. 既存フローの「充電できるか」の質問で「充電できない」を選んだ人には、手元スイッチ（電源オン）の写真と診断動画をお願いしない（撮れないため）。充電器に載せた写真はお願いする。金額はオーナー判断。
9. 足りないまま［次へ］を押したときの確認は、フロー全体で**最初の1回だけ**（文言は 7.）。
10. お客さんへの説明は「金額が下がる**可能性があります**」。「下がります」と言い切らない。

| 3 | 前輪・後輪の左右 | ○ | ○ | 4 | 4枚届いたら自動 |
| 4 | 前カゴ・荷台 | ○ | ○ | 0〜2 | 2枚届いたら自動、または［次へ］ |
| 5 | 鍵を挿した状態、型番・ロット番号 | – | ○ | 2 | 2枚届いたら自動 |
| 6 | 診断動画（写真2〜3枚でも可） | – | ○ | 動画1 または写真2〜3枚 | 動画が届いたら自動、写真の場合は［次へ］ |
| 7 | 充電器に載せた状態 | – | ○ | 写真か動画1 | 届いたら自動 |
| 8 | 気になる傷や不具合 | ○ | ○ | 0以上 | ［次へ］のみ |

バッテリー単体は4ステップ：B1 写真4枚（1〜4）→ B2 診断動画（写真2〜3枚でも可）→ B3 充電器に載せた状態（写真か動画）→ B4 気になる点。

- 進捗表示は「◯/8」（一般車は「◯/5」、単体は「◯/4」）。
- **最初の案内**：**まず最初のまとまり（3枚）を提示する**。全体の枚数と動画の本数はそのあとに短く添える（主役にしない）。所要時間は全体の「約◯分」ではなく**「1つのまとまりで1〜2分」**と刻んで見せる（オーナー計測）。撮影マップ、「できる範囲で大丈夫です」「写真が少ないと金額が下がる可能性があります」「ご家族に撮ってもらってもOKです」「今そばになくても、あとで続きから送れます」。
- **各まとまり**：番号、撮る場所と枚数、合成見本画像、残り枚数。届いたら「◯枚受け取りました。次は…」と返す（返事はまとまり単位。1枚ごとに返さない）。
- 枚数が決まっているまとまりは、枚数に達したら自動で次へ。想定より多く届いた分も受け取り、そのまとまりに紐づける。
- すべてのまとまりに［次へ］を置く（足りないまま進める）。まとまり4・8は［次へ］で飛ばす。ボタン名は実装時に短く調整してよい（例：まとまり4「付いていない」、まとまり8「特にない」）。
- 「充電できない」を選んだ人（2.1-8）：電動のまとまり2から手元スイッチを外し、まとまり6を飛ばす。バッテリー単体は B2 を飛ばす。
- 同時に送られた写真は1つの受信としてまとめ、返事は1回（技術メモ 10.）。
- 写真ステップ以外で届いた画像は、フローを進めずに短い案内文を1回返す（セッション状態で判定。旧ボットの「状態に関係なく postback が動く」不具合を繰り返さない）。
- 途中で止まった人：最終操作から24時間でオーナーに通知（1セッション1回だけ）。お客さんへの自動の声かけはしない。ただし**最初の案内で「あとで続きから送れます」と伝える**（自動の催促はしないが、再開できること自体は知らせる）。再開したときは必ず現在地を出す（例：「【3/8】の続きから送れます」）。
- 終了時：「写真ありがとうございました。確認して金額をLINEでお送りします」と返し、既存フローの次のステップ（防犯登録の質問など）へつなぐ。確定額の送り方は現行どおり（Phase 0 で確認）。

### 2.4 見本画像

- 実写風の画像に**赤い点線の枠＋番号**を重ねる。枠は「大きく写してほしい範囲」、番号は撮影マップと一致させる。
- 素材：オーナーが Gemini で生成した11枚（2.2 の「見本」列の番号。受け渡し時のファイル名で読み替える）。すべて正方形。
  - 右下の星マーク（生成AIの印）は切り落とす。
  - 3348（BRIDGESTONE の文字）と 3345（KENDA の文字）は、オーナーが文字を消してから渡す。
- 実写真が必要な箇所（品番シール、手元スイッチ、型番・ロット番号、バッテリー単体の正面・横・端子）：オーナーが実写真を用意する。**用意できるまでは見本画像なし（説明文だけ）で動く作り**にし、後から差し替えられるようにする。
- 撮影マップ：クロコが SVG で作る。横から見た自転車の線画に番号付きの丸を置く。一般車・電動・バッテリー単体の3種。LINE 用に PNG も書き出す。
- 合成画像：まとまりごとに1枚（2〜4コマ、各コマに番号と短い名称）。個別画像は撮影ガイドページで使う。
- 前輪・後輪は片側の見本1枚ずつ。キャプションに「反対側からも同じように1枚」。
- 置き場所：サイトの assets（既存の置き方に合わせる）。LINE からはその URL を画像メッセージで送る（HTTPS。元画像とプレビュー画像のサイズ上限は LINE 公式ドキュメントで確認して合わせる）。
- **文字が命の4箇所（品番シール、手元スイッチ、バッテリーの型番・ロット番号、端子）だけは「良い例／悪い例」を並べた見本にする。** 悪い例は「遠すぎて文字がつぶれている」1枚でよい。撮影ガイドページと LINE の該当まとまりで使う。
- 生成画像の元データはリポジトリに入れない（加工後の配信用ファイルだけ入れる）。

### 2.5 診断動画

- 既存の見本動画（全メーカー共通・1本）を使う。「速すぎて追いつけない」という指摘があるため編集する。編集はクロコ（ffmpeg）。
- 編集方針：
  - 長押しなど時間が大事な場面は**実際の速さのまま**にし、画面に秒数のカウントを重ねる（全体を遅くすると押す時間を間違える原因になる）。
  - 大事な場面の前後で2〜3秒止め、「次はここを押します」のような字幕を入れる。
  - 手の動きが速い部分だけ少し遅くする。
  - 字幕はスマホで読める大きさ。フォントは動画に使えるライセンスのもの（Noto Sans JP など）。
- 手順（承認2回）：
  1. 元動画を受け取り、場面ごとに画像を切り出して内容を確認する。
  2. 「時刻／場面／処理（止める・遅くする・字幕の文言）」の一覧を出す → **オーナー承認**。
  3. 編集する。
  4. 完成版とサムネイル（JPEG）を出す → スマホで確認 → **オーナー承認**。
  5. 承認後に LINE（動画メッセージ）とサイト（診断ページ）で使う。
- 出力：mp4（H.264 / AAC）、720p 目安。ファイルサイズは GitHub Pages で配信できる範囲に収める（目安 20MB 以下）。LINE の動画上限とサムネイルの要件は公式で確認する。
- 元動画はリポジトリに入れない（作業用フォルダに置く）。

### 2.7 現物が写真と違ったとき（運用ルール。文言に反映する）

- 当日は金額を上げも下げもしない。
- 小さな違い（写真でわかる程度の傷・汚れ・錆、空気が抜けているなど）は、確定額のまま買い取る。
- 大きな違いはその日の取引を見送る。対象は次の5つ：
  1. 電源が入らない・アシストしない
  2. 写真と別の車体やバッテリー
  3. 鍵が合わない・開かない
  4. バッテリーの膨らみ・液漏れ
  5. 写真になかった大きな破損
- 見送りのときは出張費をいただかない。その場では金額を出し直さない。希望があれば LINE で確定額を出し直す。
- このルールは、確定額を伝えるメッセージと撮影ガイドで事前に知らせる。
- 防犯登録・本人確認の問題は古物営業法に沿った別対応（本書の対象外）。
- 「当日金額を変えない」運用と見送りの扱いについて、**この事業は特定商取引法（訪問購入）に当てはまらないとオーナーが確認済み（2026-09-22）。クーリングオフ・書面交付の記載は不要**。着手の条件は解消した。

## 10. 技術メモ（LINE / GAS。制約と実装のヒント。数値は公式で要確認）

- **同時送信の画像**：複数枚を同時に送ると1枚ずつ別イベントで届き、各イベントの `message.imageSet` に共通の `id` と `index` / `total` が付く。古いアプリでは `index` / `total` が付かないことがあるので、**`imageSet.id` でまとめ、`index` / `total` には依存しない**。`imageSet` がない単発の画像も同じ処理で扱う。
- **返事を1回にする方法**：replyToken はイベントごとに1つで、短時間で失効し1回しか使えない。案：`total` が分かるときは最後の1枚の replyToken で返す。分からないときは、最後の受信から一定時間（例：8秒）経過後に時間トリガーで push を1回送る。push は月の無料枠を消費するので、reply で済む場合は reply を優先する。
- **画像・動画は保存しない**（2026-09-22 決定。Phase 0 で現行も保存していないことを確認）。ボットは枚数とまとまりを記録するだけで、写真そのものはオーナーが LINE のトークで見る。コンテンツ取得 API は使わない（webhook を重くしない・保管責任を増やさないため）。
- **セッション状態**：写真ステップにいるか、どのまとまりか、各まとまりの受信数、［次へ］確認済みか、24時間通知済みか、を持つ。
  **写真セッションは Sheets に 7日間（確定額の有効期限と同じ）保持する**（2026-09-22 決定）。CacheService は高速化の前段として残すが、現行は Sheets 側も 6時間で切っているため（`v2-core.gs`）、そこを写真セッションだけ延ばす。キャッシュが消えても Sheets から復元して続きから進める。postback と画像の受付はこの状態で判定する。
- **見本の送信**：画像メッセージ（元画像 URL とプレビュー画像 URL、HTTPS）。動画メッセージにはサムネイル画像が必要。サイズ上限は公式ドキュメントで確認して合わせる。
- **webhook の応答**：GAS の `doPost` は速やかに 200 を返す。重い処理（Drive 保存、合成通知）は失敗しても受付が止まらないようにする。
- **時間トリガー**：24時間停止の検出（例：1時間ごと）と、まとめ返信の遅延処理（例：数分ごと。細かい間隔が難しい場合は「最後の1枚で reply」を主にする）。
- **配信ファイル**：見本画像は 1:1、JPEG、プレビュー用は上限内に収める。動画は mp4（H.264 / AAC）。GitHub Pages の1ファイルサイズ制限に注意。
