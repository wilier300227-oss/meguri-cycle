## 1. 背景

| # | 事象 | 原因 |
|---|---|---|
| A | 買取希望と明示済みの顧客に「処分の出張費 1,500〜2,000円」を自動送信 | 意向を見ずに市町名の部分一致で発火 |

## 4. 実装済み修正に対する指摘（要手直し）

### 4-1. 市町名ゲート（3-1）に残る穴

| 課題 | 対応 |
|---|---|
| 意向で内容を出し分けていない | 買取意向なら「査定・出張とも無料」のみ返す。処分意向のときだけ出張費を返す |
| 予算2の数え方が不明確 | **テキストメッセージのみカウント**。画像・スタンプでは減らさない |
| 疑問文が除外されていない | 「？」「でしょうか」「ますか」「可能」「いつ」「いくら」を含む場合は料金を返さず §5-3 の通知へ（事象B の再発防止） |
| 保存先 | `CacheService.getScriptCache()` にuserIdをキーとして保持。読み書きは `LockService` で保護。Propertiesは競合と上限のため不可 |
| 上位ルールの不在 | 停止フラグ／手動対応モード／S4以降では、ゲートが開いていても金額を返さない（事象C の再発防止） |

### 4-2. 写真の完全無応答（3-2）は行き過ぎ

庄司さんは4台分を20分かけて送信。既読のみだと到達不安が残る。

- **セッション最初の1通にだけ**短い受領確認を返す
- 文面：受領＋「送り終えたら〈査定をお願いします〉を押してください」＋48時間の目安
- デデュープ：30分（同一セッション中の2通目以降は無応答）
- これにより 3-4 のボタン到達率も上がる

### 4-3. 48時間の集約（3-3）の残作業

- **LINE管理画面側の応答メッセージ（友だち追加時の挨拶文）に「48時間以内」が残っていないか確認・削除**。GASだけ消しても二重管理は解消しない
- 集約先は 4-2 の受領確認と `replyEstimateRequest` の2か所に限定

### 4-4. `replyEstimateRequest`（3-4）の「現地減額」は要差し替え【重要】

**現状の矛盾**：挨拶文には「お伺いするのは金額が決まったあとです。査定のためだけの訪問は承っておりません。玄関先で価格を交渉することがないよう、先に金額を確定させています」と明記している。一方で「現地で減額の可能性」を自動送信すると、この約束が崩れる。

**差し替え方針：条件付き確定額**

```
写真のとおりであれば〇〇円で確定します。

写真では判別できない次の点が現地で見つかった場合のみ、
その場では決めず、一度お持ち帰りのうえ再提示します。
・フレームの曲がり、割れ
・変速またはブレーキが機能しない
・バッテリー残量ランプが2点灯以下（電動アシストの場合）
```

電動アシストは条件分岐で提示する（例：4点灯なら30,000円／3点灯なら24,000円／2点灯以下は18,000円）。事前に金額が確定するため、特商法 訪問購入の適用除外（第58条の17第2項第1号）の前提を維持できる。

**その他の修正**

- 住所は**町名まで**に留める。番地は金額合意後・日程確定時に取得（個人情報の最小化）
- ボタン文言「入力完了」は実態と合わない → 「写真を送り終えた／査定を依頼する」
- §5-5 の必須項目をここで回収する

### 4-5. `replyInquiry`（3-5）の不足

- **クイックリプライは次のメッセージで消える**。人への導線は常設のリッチメニュータイルにする（§6）
- 押された時点で**手動対応モードON**（§5-1）。これがないと人が対応中に別キーワードで自動応答が割り込む
- **オーナー通知の実装がない**。通知がないと問い合わせが埋もれる（事象F）

## 5. 新規実装タスク（7項目）

### 5-1. 手動対応モード

**目的**：人が対応している間、自動応答を完全に止める。

| 項目 | 内容 |
|---|---|
| 発動 | `action=inquiry` タップ／管理者がSheetsのフラグ列をON／§5-3 の通知が発火した時 |
| 動作 | 該当userIdへの**全自動応答を停止**。ログ記録とオーナー通知のみ継続 |
| 解除 | 管理者操作、または48時間経過で自動解除 |
| 保存 | Sheets（`manual_mode` / `manual_until`）。CacheServiceは揮発するため不可 |
| 例外 | 解除後も期限文言（48時間以内）は再送しない |

### 5-2. 停止フラグ（再勧誘禁止）

**目的**：特商法 第58条の6第3項（再勧誘の禁止）への対応。

| 項目 | 内容 |
|---|---|
| 発動 | メニューB「キャンセル・やめる」／「不要」「やめます」「結構です」等の検知／取引完了の記録時 |
| 動作 | 金額・営業・案内系メッセージを**一切送信しない**。新規問い合わせには「担当者が確認します」1文のみ返しオーナー通知 |
| 解除 | **顧客からの明示的な再依頼のみ**。時間経過では解除しない |
| 保存 | Sheets（`opt_out` / `opt_out_at` / `reason`） |

**評価順序の最上位**に置く。他のどの分岐よりも先に判定する。事象C の根本対策。

### 5-3. 分類不能テキスト → オーナー通知

**目的**：人が答えるべき質問にボットが誤答しない。通知の遅延をなくす（事象B・F）。

- 既知の意図（買取／処分／エリア／査定依頼／FAQ／相談）のいずれにも一致しない場合、**顧客への返信を生成しない**
- オーナーへLINE通知：userId・表示名・本文・受信時刻・現在の状態
- 顧客には無応答、または最大「担当者が確認いたします」1文のみ（1セッション1回）
- 同時に手動対応モードをON

**判定の優先順**

```
1. 停止フラグ（opt_out）
2. 手動対応モード（manual_mode）
3. postback アクション（明示タップ）
4. キーワード一致
5. 分類不能 → 何もしない＋通知   ← 既定値
```

**既定値を「何もしない」にすることが本タスクの核心。** 従来は既定値が実質「料金を返す」だった。

### 5-4. 出張費マスタの一元化

**目的**：表記ゆれの解消（事象G）。

- Sheets に `fee_master` シート：`市町名` / `出張費` / `対応可否` / `備考`
- 4段階（¥1,000〜¥2,500）を17市町に展開。**レンジ表記を廃止し市町ごと単一額**に
- GAS・挨拶文・meguri-cycle.com・Jimoty の記載すべてがこのシートを参照。**コード内ハードコード禁止**
- 挨拶文の「1,000円〜」は最安値と一致させる
- エリア外（富山・福井）は金額を出さず「要相談」を返す
- **買取意向なら金額を出さない**（買取は出張費無料。事象A の対策）

### 5-5. 複数台対応

**目的**：手動運用（「1台目」「2台目」の指示）の自動化。

- 申込直後に**台数を質問**（1台／2台／3台／4台以上のクイックリプライ）
- 車両ごとにレコード生成：`userId + 車両番号`
- 写真は「〇台目」の宣言で振り分け。宣言がなければ直近の車両に紐付け
- 車両単位で保持：メーカー・車種・電動アシスト有無・防犯登録名義・査定額・状態
- **防犯登録の名義を申込時に取得**（本人／家族／不明）。庄司さんの4台は本人・妻・長男・次男の別名義だった。抹消手続きと本人確認に関わるため査定額連絡時ではなく初回に聞く
- 査定額連絡は1台ずつ内訳＋合計を提示
- 既存の取引記録システム（Sheets）と同一の車両IDで突合できる設計にし、訪問時にタブレットへ引き継ぐ

**S1で必ず取得する項目（1回にまとめる）**

```
台数 ／ 市町名・町名 ／ メーカー・車種 ／ 電動アシストの有無
／ 防犯登録の名義（本人・家族・不明） ／ 希望（買取・処分）
```

### 5-6. webhookEventId デデュープ

**目的**：LINEの再送による二重送信の防止。

- 各イベントの `webhookEventId` を CacheService に10分保持
- 既存なら即 `return`（処理も返信もしない）
- 書き込みは `LockService` で保護
- **Webhookは即座に200を返し**、重い処理は後段へ回す
- 現行の「10分デデュープ」は内容ベースと思われるが、eventIdベースのほうが確実かつ軽量

### 5-7. 全受信メッセージと発火分岐のログ

**目的**：誤爆の診断を可能にする。今回の原因特定に時間を要した直接の原因。

Sheets に `log` シート、1イベント1行。

| 列 | 内容 |
|---|---|
| `timestamp` | 受信時刻 |
| `userId` / `displayName` | 発信者 |
| `eventType` | message / postback / follow |
| `messageType` | text / image / sticker |
| `body` | 本文（画像はファイルID） |
| `state` | その時点の状態 |
| `matchedRule` | 発火した分岐名（分類不能なら `UNMATCHED`） |
| `replySummary` | 返信の1行要約（無応答なら `NONE`） |
| `flags` | manual_mode / opt_out / expect_city の状態 |

`UNMATCHED` 行を週次で確認し、FAQ追加・分岐新設の判断材料にする。

| T5 | 写真を20分間に十数通連投 | **最初の1通のみ**受領確認。以降は無応答（事象E） |
| T6 | 「直接見にきていただく事は可能でしょうか？」 | 顧客へは無応答または1文のみ。**オーナーへ即時通知**（事象F） |
| T7 | 「対応エリア」タップ → 「かほく市」 | `fee_master` の固定額を返す。他経路の数値と一致（事象G） |
| T8 | 同一 `webhookEventId` を2回受信 | 2回目は無処理・無返信（5-6） |
| T9 | 「やめます」送信後に任意のメッセージ | 営業メッセージを送らない。通知のみ（5-2） |
| T10 | 全ケース | `log` シートに `matchedRule` と `replySummary` が記録される（5-7） |

---

## 10. 禁止事項（例外なし）

1. **顧客向け文面に「転売」を使わない。**「リユース品価格調査」で統一
2. **停止フラグが立っているユーザーへ営業メッセージを送らない**（特商法 第58条の6第3項）
3. **金額を範囲（レンジ）で提示しない。**固定額または条件付き確定額のみ（訪問購入の適用除外の前提）
4. **S3以降で金額を自動送信しない**
5. **住所は町名までしか自動で聞かない。**番地は金額合意後
6. **出張費をコードにハードコードしない。**`fee_master` を唯一の情報源とする
7. **.env をコミットしない。**LINEトークンは `PropertiesService` 経由
8. **公開物に個人名・郵便番号・電話番号を載せない**
9. 玄関先での価格交渉を前提とする文面を作らない（挨拶文の約束との整合）

## 11. 補足

- 特商法 訪問購入の適用除外（第58条の17第2項第1号）は石川県 生活安全課に電話確認済み。ただし以下3点の義務は残る
  - 氏名等の明示（第58条の5）
  - 勧誘意思の確認（第58条の6第2項）
  - 再勧誘の禁止（第58条の6第3項）→ §5-2 で対応
- 古物営業法の帳簿要件は既存のタブレット取引記録システムで充足
- 個人情報保護法：Gboard の学習によるオートコンプリート露出への対策（学習データの消去、非標準 autocomplete トークン）は取引記録システム側の課題として別途対応
